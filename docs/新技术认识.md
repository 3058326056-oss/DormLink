## 1. 结论速览

**一句话结论**：ArkUI 状态管理 V2（`@ComponentV2` / `@ObservedV2` / `@Trace`）自 **API version 12** 起支持、**API version 19** 起放宽 V1/V2 混用，在当前最新官方文档中已被建议用于新开发应用；但《栖居联动》是扁平可序列化状态 + 4 页签小规模 UI + 模板工程 V1，V2 的深度观测收益不足以抵消全量迁移与回归成本，故本期**定稿使用 V1**，V2 作为数据模型设计依据与 P2 演进路线。

## 3. 用途：这项技术解决什么问题

| 能力 | 官方要点 | 出处 |
|---|---|---|
| 深度观测嵌套类属性 | `@ObservedV2` + `@Trace` 让嵌套类属性变化可直接触发 UI 刷新；V1 无法直接观测嵌套类属性变化，只能靠 `@ObjectLink` 逐层拆自定义组件，层级深时代码复杂、易用性差 | S2 |
| 精准刷新 | 被 `@Trace` 装饰的属性变化时，**仅通知该属性关联的组件**刷新；未装饰的属性在 UI 中无法感知变化 | S2 |
| 状态与组件解耦 | V1 侧重组件层级状态管理；V2 把观察能力增强到数据对象本身，支持更灵活的数据操控与更高效的 UI 刷新 | S3 |
| 变化前值可获取 | V2 的 `@Monitor` 不仅能感知变化后的数据，还能获取变化前的数据 | S3 |
| 组件冻结（配套能力） | `@ComponentV2` 支持 `freezeWhenInactive`，非激活组件不响应状态更新，减少无效刷新 | S4、S5 |

## 4. 适用版本（明确版本线，均引官方原文）

| 版本线 | 能力 / 结论 | 官方原文依据 | 出处 |
|---|---|---|---|
| **API version 12** | `@ObservedV2` 与 `@Trace` 装饰器开始支持；同版本起支持在 ArkTS 卡片、元服务中使用 | 「@ObservedV2与@Trace装饰器从API version 12开始支持」 | S2 |
| **API version 12** | `@ComponentV2` 装饰器开始支持；`@ComponentV2` 组件冻结开始支持 | 「@ComponentV2装饰器从API version 12开始支持」；「从API version 12开始，支持@ComponentV2装饰的自定义组件冻结功能」 | S4、S5 |
| **API version 19** | V1/V2 混用约束**减少**，新增 `enableV2Compatibility`、`makeV1Observed` 辅助迁移 | 「从API version 19开始，减少了对状态管理V1和V2混用场景的约束」 | S8 |
| **API version 26 之前** | 混用校验严格：V1 传 V2 仅支持简单类型，V2 状态变量传 V1 时 `Array/Set/Map/Date` 不支持 | 官方《混用指导（API 19 之前）》限制条件 | S9 |
| **当前最新文档**（该页未标注文档版本号，按 26.0.0 系列理解） | 官方对新开发应用的建议是 **V2**；对已用 V1 且满足需求的应用，**无需立即切换** | 「对于新开发的应用，建议直接采用V2版本进行开发」「对于已使用V1的应用，如果V1的功能和性能满足需求，无需立即切换至V2」 | S3 |
| **API version 26.0.0** | ArkUI 仍在演进：组件参数新增 `reusePool` 全局复用池，**起始版本 26.0.0** | 「起始版本：26.0.0」 | S5 |

> **与本项目环境的关系**：本工程 `targetSdkVersion 26.0.0`、`compatibleSdkVersion 6.1.1(24)`，均 ≥ API 12，因此 V2 **在技术上可用**；但「可用」不等于「该用」，判断见第 6 节。

## 5. 局限（含对《栖居联动》的实际影响）

| # | 局限 | 官方依据 | 对《栖居联动》的实际影响 |
|---|---|---|---|
| L1 | `@ComponentV2` 与 `@Component` **不能同时装饰同一个 struct**；V1/V2 装饰器不能在组件内混用，否则编译报错 | S4、S8、S9 | 4 个页签必须整套统一，无法「逐页渐进试水」；本期模板工程是 V1，选 V2 需 4 页全量重写 |
| L2 | `@ComponentV2` 装饰的组件**暂不支持组件复用、LocalStorage** | S4 | 本项目日志列表/规则列表若后期做长列表复用，需重新评估；本期规模小，不构成阻塞 |
| L3 | V1 装饰器**不能与 `@ObservedV2` 一起使用**；API 19 放宽混用后该禁止**依旧维持**；V2→V1 用装饰器接收 `@ObservedV2` 类会编译报错 | S8 | 若把 `AppState` 改成 `@ObservedV2` 类，现有 `@State` / `@Provide` 体系须整体替换，且 Preferences 的 `JSON.parse` 后显式校验流程要重写 |
| L4 | `@ObservedV2` 与 `@Trace` 必须**配合 `new` 实例化**才具观测能力，单独使用任一装饰器无效 | S2 | 冷启动 `restore()` 是从 JSON 反序列化的普通对象，而非 `new` 出来的被装饰实例；直接套 V2 会在「重启恢复」这一核心验收点上引入额外构造逻辑与风险 |
| L5 | 编译器、工具链、DevEco Studio 会对误用/混用做校验；双重代理（数据被 V1 与 V2 同时代理监听）会带来不确定性 | S3 | 独立完成、无人协助排查，混用导致编译/刷新异常会直接威胁 8 次提交里程碑与交付时间 |
| L6 | 官方论坛技术支持答复列举：V2 下 `animateTo` 动画可能异常、部分高级组件 / `WithTheme` / `@Reusable` 暂未提供，这些场景**推荐 V1** | S10（官方论坛，**非正式规范**，可靠性低于 S2–S5，仅作补充） | PRD 5.3 明确要求设备卡状态变化有动画与 Toast 反馈，动画异常风险是「不采用」的直接业务理由 |
| L7 | 26.0.0 新增的 `reusePool` 必须与 `poolAccepts` 同时配置且后者为非空数组，否则编译错误 | S5 | 印证 V2/ArkUI 能力仍在迭代，本期不引入 26.0.0 新增组件能力可避免「追新踩坑」 |

## 6. 这项技术在本项目里用在哪（本人判断）

**定位**：V2 **不落入本期 UI 源码**，但落在 3 个可核验的架构决策上——这不是「没用」，而是「评估后显式不采用并记录依据」。

| 落点 | 具体体现（可核验位置） | 判断内容 |
|---|---|---|
| D1 **数据模型形状** | `docs/软件需求说明书.md` 第 3.1 节 `AppState` / `DeviceStateMap` / E11；第 8.2 节序列化约定 | 正因为 V1 无法深度观测嵌套属性（S2），`AppState` 被刻意设计为**扁平 `Record<string,string>` + 数组 + 整体替换**，每次 `evaluate()` 返回新的 `nextDevices`，而不是原地改深层字段；这既规避 V1 缺陷，又契合 Preferences 单文档 `JSON.stringify` 整体写入 |
| D2 **状态管理版本定稿** | `docs/软件需求说明书.md` 附录 B 的 **B7**（统一 V1，V1/V2 装饰器不可混用）、第 5.1 节 M5 ViewModel | 依据 S3「已使用 V1 且满足需求无需立即切换」+ L1/L5/L6，定稿 V1；评分项「正确使用状态管理」考察正确性而非版本新旧 |
| D3 **P2 演进路线** | `docs/软件需求说明书.md` 第 2.5 节 P2、第 12 章 Q6/Q7 | 若后续做「多房间 / 嵌套规则分组 / 长日志列表」，`@ObservedV2 + @Trace` 是候选升级路径；届时按 S3 的逐步迁移策略分阶段改造并全量回归 |

**收益 / 成本对照（为何不迁移）**

| 维度 | 迁到 V2 的收益 | 本项目的实际成本 | 结论 |
|---|---|---|---|
| 深度观测 | 嵌套对象属性可直接刷新 | 现有模型已扁平化，**无深层嵌套痛点** | 收益≈0 |
| 刷新粒度 | 仅刷新关联组件 | 4 张设备卡 + 3 条 Slider，整体替换已足够流畅 | 收益可忽略 |
| 迁移成本 | — | 4 个页面全量重写 + `@Provide/@Consume` 替换 + 冷启动反序列化构造逻辑改造 | 高 |
| 回归成本 | — | 12 条单测虽与 UI 解耦，但 8 步人工验收链路与 4 张截图需全部重做 | 高 |
| 交付风险 | — | 独立完成、无并行排查人力；L5 双重代理与 L6 动画异常一旦出现即影响交付 | 不可接受 |

> **一句话判断**：在 26.0.0 官方推荐 V2 的背景下，本作品仍选 V1，是基于**数据模型扁平、UI 规模小、模板工程 V1、独立完成、动画反馈必需**这 5 个具体约束做出的取舍，而非不了解新技术。
