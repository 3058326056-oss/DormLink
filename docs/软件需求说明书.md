## 2. 需求与问题分析

### 2.1 目标用户

| 用户 | 场景 | 关注点 |
|---|---|---|
| 高校宿舍学生（主用户） | 想让照明、通风、空调、窗帘按环境自动配合，但无真实硬件 | 规则好不好写、结果看不看得懂、冲突能不能解释 |
| 课程评审 / 验收者（次用户） | 需在模拟器上快速核验功能与证据 | 状态变化是否可见、日志是否可回溯、重启是否恢复 |
| 开发者本人（独立完成者） | 需在无设备、无网络环境下跑通与自测 | 引擎可脱离 `@ohos.*` 运行、可用 Local Unit Test 验证 |

### 2.2 用户痛点

| # | 痛点 | 本作品对应解法 |
|---|---|---|
| P1 | 宿舍设备各自为政，夜间/高温/潮湿需要手动逐个操作 | 一次性编排规则，环境变化自动联动 4 类设备 |
| P2 | 多条规则同时命中同一设备时结果不可预期 | 定稿优先级 + 稳定执行顺序 + 冲突抑制并在日志中留痕 |
| P3 | 自动化「黑盒」，不知道为什么设备变了 | 每条执行记录含触发条件实测值、设备变化、执行顺序、被抑制动作 |
| P4 | 无真实 IoT 硬件与云平台，无法演示 | 纯内存 Mock 环境 + 3 组可复现预设场景 |
| P5 | App 一关配置就丢，无法形成持续使用 | Preferences 全量持久化 + 冷启动恢复 |

### 2.3 产品目标（3 个正交目标）

| 目标 | 内容 | 可度量判据 |
|---|---|---|
| G1 **可编排** | 用户能自主定义、修改、启停规则并立即生效 | 预置 5 条规则，CRUD + 启停 + 优先级调整全部可用；双条件 AND 规则存在且生效 |
| G2 **可解释** | 每次联动的触发条件、执行顺序、设备变化、冲突裁决都可追溯 | 每次评估生成 1 条 `ExecutionRecord`，含 `conditionTraces` / `entries` / `deviceChanges` / `executionOrder` |
| G3 **可延续** | 状态跨进程存活且逻辑可自动验证 | 杀进程重启后设备/规则/环境/日志一致；≥12 条 Local Unit Test 真实运行通过 |

### 2.4 用户故事

| # | 用户故事 |
|---|---|
| U1 | 作为学生，我想新增一条「温度 ≥30 时开空调制冷」的规则并设置优先级，以便按自己的习惯自动控温 |
| U2 | 作为学生，我想拖动滑杆调整温度/湿度/光照，以便立刻看到 4 类设备的联动变化 |
| U3 | 作为学生，我想查看一条执行记录里的触发条件实测值与执行顺序，以便理解某次设备为何变化 |

## 3. 数据与状态分析

> 本章字段名为**冻结契约**，源码中的类型定义、JSON 键名、日志序号必须与之一致（评分项「内容完整且与源码一致」）。

### 3.1 关键数据实体

**E1 `EnvironmentSnapshot` — 环境快照**

| 字段 | 类型 | 说明 |
|---|---|---|
| `temperature` | `number` | 室内温度，℃ |
| `humidity` | `number` | 室内湿度，%RH |
| `illuminance` | `number` | 光照强度，lx |
| `updatedAt` | `number` | 最后修改时间戳（ms，由调用方传入） |

**E2 `DeviceStateMap` — 设备状态表**：`Record<DeviceId, string>`，`DeviceId ∈ {'light','fan','ac','curtain'}`，值为该设备状态枚举字符串（见 7.1）。

**E3 `Rule` — 联动规则**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `string` | 稳定唯一标识，如 `'R3'`；同优先级裁决的字典序依据 |
| `name` | `string` | 规则名称（UI 展示） |
| `enabled` | `boolean` | 是否参与评估 |
| `priority` | `number` | 整数 1–100，**数值越大优先级越高** |
| `logic` | `string` | 本期固定常量 `'AND'` |
| `conditions` | `Condition[]` | ≥1 条；本期按 AND 组合 |
| `actions` | `RuleAction[]` | ≥1 条；同一规则内不得对同一 `deviceId` 重复动作 |
| `createdAt` / `updatedAt` | `number` | 时间戳 ms |

**E4 `Condition`**：`field: 'temperature'|'humidity'|'illuminance'`、`op: 'GT'|'GTE'|'LT'|'LTE'|'EQ'`、`threshold: number`。

**E5 `RuleAction`**：`deviceId: string`、`targetState: string`（必须属于该设备状态枚举）。

**E6 `ConditionTrace` — 触发条件留痕**：`ruleId: string`、`field: string`、`op: string`、`threshold: number`、`actual: number`、`passed: boolean`。

**E7 `LogEntry` — 动作级日志条目**

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq` | `number` | **从 1 起**，按排序后的全量候选动作序列编号（含被抑制/无变化条目） |
| `ruleId` / `ruleName` | `string` | 来源规则 |
| `priority` | `number` | 来源规则优先级 |
| `actionIndex` | `number` | 动作在规则内的声明序号（从 0 起） |
| `deviceId` / `targetState` | `string` | 目标设备与目标状态 |
| `fromState` / `toState` | `string` | 评估前 / 评估后状态（`SUPPRESSED` 时 `toState = fromState`） |
| `status` | `'APPLY' \| 'NO_CHANGE' \| 'SUPPRESSED'` | 执行 / 目标态已满足 / 因冲突被抑制 |
| `suppressedByRuleId` | `string` | 仅在 `SUPPRESSED` 时有值，指向胜出规则 id |
| `reason` | `string` | 人类可读原因，如 `'同设备冲突，R3(80) 优先于 R2(60)'` |

**E8 `DeviceChange`**：`deviceId: string`、`fromState: string`、`toState: string`、`ruleId: string`、`seq: number`。

**E9 `ExecutionRecord` — 一次评估的执行记录**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `string` | 记录唯一 id（由调用方生成） |
| `timestamp` | `number` | 评估时间 ms（由调用方传入 `now`） |
| `sceneId` | `string` | 场景 id 或 `'CUSTOM'` |
| `snapshot` | `EnvironmentSnapshot` | 本次输入快照（**原样留档**） |
| `matchedRuleIds` | `string[]` | 命中规则 id **去重**后按 `priority DESC → ruleId ASC` 排序的列表 |
| `conditionTraces` | `ConditionTrace[]` | **触发条件**（含未通过项，便于解释） |
| `entries` | `LogEntry[]` | 动作级日志，按 `seq` 升序 |
| `deviceChanges` | `DeviceChange[]` | **设备变化**（仅 `APPLY`） |
| `executionOrder` | `number[]` | **执行顺序**：所有 `status='APPLY'` 的 `seq` 升序数组 |
| `conflictCount` | `number` | `SUPPRESSED` 条目数 |

**E10 `AppState` — 持久化根对象**

| 字段 | 类型 | 说明 |
|---|---|---|
| `schemaVersion` | `number` | 当前 `1` |
| `devices` | `DeviceStateMap` | 4 类设备当前状态 |
| `environment` | `EnvironmentSnapshot` | 当前环境快照 |
| `rules` | `Rule[]` | 全部规则（含停用） |
| `records` | `ExecutionRecord[]` | 历史执行记录，上限 **200** 条，FIFO 淘汰 |
| `activeSceneId` | `string` | 当前选中场景 id |
| `lastUpdatedAt` | `number` | 最后写盘时间 ms |

**E11 `EvaluateInput` / `EvaluationResult` — 引擎契约**

```
EvaluateInput    { snapshot, rules, devices, sceneId, now, recordId }
EvaluationResult { record: ExecutionRecord, nextDevices: DeviceStateMap,
                   matchedRuleIds: string[], rejected: boolean }
```

> `rejected=true` 表示输入快照非法：此时 `record` 为**空记录**（`entries=[]`、`matchedRuleIds=[]`、`conflictCount=0`）、`nextDevices` 与入参 `devices` 相同；**ViewModel 不得把它追加进 `records`、不得写盘**，仅提示「环境数据非法」。该设计让异常路径也能被纯逻辑单测覆盖。

### 3.2 状态变化

| 状态主体 | 取值 / 变化 | 触发事件 | 变化后副作用 |
|---|---|---|---|
| 环境快照 | 3 项数值在合法区间内变化 | 滑杆松手提交 / 加载场景预设 | `updatedAt` 更新 → 写盘 |
| 设备状态 | 4 类枚举值单步跳变（`from → to`） | 引擎 `APPLY` / 手动单点控制（P1） | 设备卡动画 + Toast + 写盘 |
| 规则集合 | 新增/修改/删除/启停/优先级 | 规则页保存 | 立即影响下一次评估 → 写盘 |
| 规则命中态 | 每次评估重新计算，**不持久化** | `evaluate()` | 写入 `ExecutionRecord` |
| 执行记录 | 追加 1 条（超 200 淘汰最旧） | `evaluate()` | 日志页刷新 + 写盘 |
| 应用生命周期 | `未恢复 → 已恢复`（冷启动 `restore()`） | `EntryAbility` 启动 | 渲染真实状态或回落默认态 |

> **重要**：`evaluate()` 为**纯函数**，不修改入参、不读写全局状态、不调用时间/随机/系统 API；相同输入必得相同结果，保证幂等与可测。

## 7. 具体设定（定稿）

### 7.1 4 类可控设备

| `deviceId` | 名称 | 状态枚举（默认值**加粗**） | 可选动作（映射到目标状态） | 默认初态 |
|---|---|---|---|---|
| `light` | 主灯 | `OFF` **/ `ON` / `DIM`**（关 / 全亮 / 柔光） | `TURN_ON→ON`、`TURN_OFF→OFF`、`SET_DIM→DIM` | `OFF` |
| `fan` | 排风扇 | **`OFF`** / `LOW` / `HIGH`（停 / 低速 / 高速） | `SET_OFF→OFF`、`SET_LOW→LOW`、`SET_HIGH→HIGH` | `OFF` |
| `ac` | 空调 | **`OFF`** / `COOL` / `HEAT`（停 / 制冷 / 制热） | `SET_OFF→OFF`、`SET_COOL→COOL`、`SET_HEAT→HEAT` | `OFF` |
| `curtain` | 智能窗帘 | **`CLOSED`** / `HALF` / `OPEN`（关闭 / 半开 / 全开） | `SET_CLOSED→CLOSED`、`SET_HALF→HALF`、`SET_OPEN→OPEN` | `CLOSED` |

> 规则动作用 `targetState` 直接表达；上表动作名用于 UI 文案与 P1 手动控制。所有状态值为**字符串枚举**，可直接 JSON 序列化。

### 7.2 3 项可调整环境数据

| `field` | 名称 | 单位 | 取值范围 | 默认值 | Slider 步长 | 钳制边界 |
|---|---|---|---|---|---|---|
| `temperature` | 室内温度 | ℃ | `0 – 45` | `26` | `1` | `clamp(v, 0, 45)` |
| `humidity` | 室内湿度 | %RH | `10 – 95` | `55` | `1` | `clamp(v, 10, 95)` |
| `illuminance` | 光照强度 | lx | `0 – 2000` | `300` | `50` | `clamp(v, 0, 2000)` |

运算符语义：`GT >`、`GTE >=`、`LT <`、`LTE <=`、`EQ ==`（**`>=` 含等号、`<` 不含等号**，由 T05 锁定）。

### 7.3 预置规则（5 条，含 2 条双条件 AND）

| id | 名称 | 条件表达式（`logic='AND'`） | 动作（`deviceId=targetState`） | 优先级 | 默认 |
|---|---|---|---|---|---|
| **R1** | 夜间补光 | `illuminance < 200` | `light=DIM` | **30** | 启用 |
| **R2** | 高温制冷 | `temperature >= 30` | `ac=COOL`，`fan=LOW` | **60** | 启用 |
| **R3** | 高温高湿强排 ★**双条件 AND** | `temperature >= 28` **AND** `humidity >= 70` | `ac=COOL`，`fan=HIGH`，`curtain=HALF` | **80** | 启用 |
| **R4** | 低温暗夜取暖 ★**双条件 AND** | `temperature <= 20` **AND** `illuminance < 500` | `ac=HEAT`，`light=ON`，`curtain=CLOSED` | **50** | 启用 |
| **R5** | 日间采光节能 | `illuminance >= 1000` | `light=OFF`，`curtain=OPEN` | **40** | 启用 |

**规则字段约束**：`id` 唯一且稳定；`priority` 整数 1–100；`conditions.length >= 1`；`actions.length >= 1`；`targetState` 必须属于对应设备枚举；同一规则内 `deviceId` 不重复。用户可新增/修改/删除/启停任意规则（预置 5 条已超过「≥4 条」要求）。

### 7.4 冲突裁决策略（定稿：`PRIORITY_FIRST`）

| 项 | 定稿规则 |
|---|---|
| 优先级数值 | `priority` 整数 1–100，**数值越大优先级越高**；R3(80) > R2(60) > R4(50) > R5(40) > R1(30) |
| 命中集合 | 仅 `enabled=true` 且**全部条件通过**的规则进入命中集合；未命中规则不产生任何动作 |
| 候选展开 | 命中规则的每个动作展开为 `ActionCandidate { ruleId, ruleName, priority, actionIndex, deviceId, targetState }` |
| 执行顺序排序键 | `priority DESC → ruleId ASC（字典序）→ actionIndex ASC`，排序后从 1 赋 `seq`；该序列即 `entries` 顺序 |
| 同设备冲突消解 | 按 `seq` 升序，每个 `deviceId` **只保留第一个候选为 winner**；其余标记 `SUPPRESSED`，并记录 `suppressedByRuleId` 与 `reason` |
| 同优先级平局 | 以 `ruleId` 字典序决出唯一 winner（结果确定、可复现、可单测） |
| winner 判定 | `targetState === 当前状态` → `NO_CHANGE`（不产生 `DeviceChange`，不计冲突）；否则 `APPLY` 并产生 `DeviceChange` |
| 执行顺序留痕 | `executionOrder = entries.filter(status==='APPLY').map(seq)`，升序；`deviceChanges` 与之同序 |
| **为什么不采用「后写覆盖」** | 后写覆盖使最终结果依赖规则遍历/数组顺序，用户无法解释「为什么空调最后是制冷」，回归测试也难以锁定；且「优先级」形同虚设，不满足作业「明确的优先级处理」。本期先做**冲突消解再执行**，结果唯一确定、日志可解释。`LAST_WRITE_WINS` 仅列为 P2 可切换策略 |

**引擎契约（伪代码，纯逻辑、零系统依赖）**

```
function evaluate(input: EvaluateInput): EvaluationResult {
  // 0) 校验 snapshot 三项数值 isFinite 且在 7.2 区间内；
  //    非法 => return { 空 record, nextDevices = input.devices 的副本,
  //                     matchedRuleIds: [], rejected: true }（不抛异常、不落盘）
  // 1) 逐条规则 traceConditions(rule, snapshot) 生成 conditionTraces（含未通过项）；
  //    enabled=true 且全部 passed => matchedRules
  // 2) 展开 matchedRules 的动作 => candidates[]
  // 3) candidates = sortCandidates(candidates)  // 赋 seq，从 1 起
  //    matchedRuleIds = candidates 来源规则去重后按 priority DESC → ruleId ASC 排列
  // 4) entries = resolveConflicts(candidates, input.devices)
  //      - 同 deviceId 首个为 winner，其余 SUPPRESSED + suppressedByRuleId + reason
  //      - winner: 同态 => NO_CHANGE；异态 => APPLY + DeviceChange + 更新 nextDevices
  // 5) 组装 ExecutionRecord { id, timestamp: input.now, sceneId, snapshot,
  //      matchedRuleIds, conditionTraces, entries, deviceChanges,
  //      executionOrder: entries.filter(APPLY).map(seq), conflictCount: 计数(SUPPRESSED) }
  // 6) return { record, nextDevices, matchedRuleIds, rejected: false }
  // 约束：不 import 任何 @ohos.* ；不调用 Date.now()/随机数；不修改入参；不落盘
}
```

## 8. 数据模型与持久化设计

### 8.1 选型与理由

| 方案 | 结论 | 理由 |
|---|---|---|
| **`@ohos.data.preferences`（选用）** | ✅ P0 | 数据规模小且为**单一文档**：4 设备 + 3 环境值 + 5 条规则 + ≤200 条日志；无联表、条件查询、事务需求；键值式读写 + `flush()` 简单可靠；只需 `JSON.stringify/parse` 即可整体序列化；便于用 `IStateRepository` 接口在单测中替换为内存实现，保证引擎与测试完全脱离系统 API |
| 关系型数据库 RDB | ❌ 本期不用 | 需建表、SQL、版本迁移与结果集映射，对本作品是过度设计；且会把数据结构耦合进 SQL 层，削弱纯逻辑模块的可测性 |
| 分布式 KV / 云 | ❌ 不做 | 超出「不要求真实硬件或云平台」范围 |

**局限与演进**：Preferences 为单文件整体读写，日志量增大后序列化会占用主线程 → 本期用 200 条上限 + 滑杆防抖 + 关键路径异步 `await` 缓解；P2 可将 `records` 单独迁到 RDB 并分页查询。

### 8.2 存储键与序列化结构

| 项 | 值 |
|---|---|
| Preferences 实例名 | `dormlink_state` |
| 主键 | `app_state` → `JSON.stringify(AppState)`（含 `schemaVersion: 1`） |
| 备用键 | `app_state_backup`（上次成功写入的副本 / 解析失败时的损坏原文） |
| 诊断键 | `last_restore_error`（可选，记录最近一次恢复异常原因） |
| 序列化约定 | 枚举一律用**字符串**；时间一律用 `number` 时间戳；不使用 `Map`/类实例直接序列化（统一为 `Record<string, string>` 与数组）；`JSON.parse` 后须显式做字段类型与白名单校验，不可直接 `as AppState` 信任 |

### 8.3 写入时机

| 事件 | 写入内容 | 时机要求 |
|---|---|---|
| 规则新增/修改/删除/启停/优先级调整 | `rules` + `lastUpdatedAt` | 校验通过后立即 `await save()` |
| 环境滑杆提交 / 场景加载与重置 | `environment`、`activeSceneId`、可选 `devices` | Slider `onChangeEnd` 提交（拖动过程不写盘） |
| 每次评估完成 | `devices` + `records`（追加 1 条，超 200 裁剪） | **先 `await save()` 再反馈成功**，避免杀进程丢最后一次联动 |
| 手动设备控制（P1）/ 清空记录 | `devices` / `records` | 立即写 |
| `onBackground` / 页面 `aboutToDisappear` | 全量兜底 | `flush()` |

### 8.4 恢复流程

```
EntryAbility.onWindowStageCreate
  → 装配 PreferencesStateRepository / MockEnvironmentProvider / RuleEngine
  → await viewModel.restore()            // UI 期间显示加载态
      → getPreferences('dormlink_state') → get('app_state', '')
      → 空串（首次启动）   → DEFAULT_STATE → save()
      → try JSON.parse
          → 校验 schemaVersion===1、必需字段存在、
            devices 键属于 4 类白名单且值属于枚举、
            rules[] 逐条 validateRule()、records[] 结构完整
          → 通过 → hydrate AppState（records 超 200 则裁剪）
          → 失败/抛错 → 原串写入 app_state_backup + 记录 last_restore_error
                       → DEFAULT_STATE + Toast「数据异常，已恢复默认配置」+ save()
  → 渲染业务页（设备卡 / 规则 / 环境 / 日志均为恢复后的值）
```

**恢复验收点**：规则（含用户新增与启停状态）、4 类设备终态、3 项环境值、历史执行记录条数与内容，四项与杀进程前逐项一致（T11）。

## 附录 B 实现约束与风险提示（面向架构师 / 工程师）

| # | 风险 / 约束 | 建议动作 |
|---|---|---|
| B1 | **Local Unit Test 不能 import `@ohos.*` 运行时 API**：一旦 `RuleEngine.ets` 或 `Models.ets` 间接引入 Preferences / UI / 时间 API，`entry/src/test/` 直接编译失败，12 条用例无法运行 | M1/M2/M3 保持纯 ArkTS；系统依赖只出现在 M4/M6/M8；依赖通过构造函数注入 |
| B2 | **SDK 双版本约束**：`compatibleSdkVersion 6.1.1(24)` / `targetSdkVersion 26.0.0` 不得改；若使用 API 26 新增能力，须评估 24 兼容或做条件调用/降级 | 变更前核对官方 API 版本表；此项同时是目标四「适用版本与局限」的现成素材 |
| B3 | **`seq` 编号是全部测试断言的基准**：7.4 的排序键与「按排序后全量候选赋 seq」一旦改动，T01/T02/T03/T05/T09/T10/T12 全部失效 | 先冻结引擎契约再编码；契约变更须同步回写本文第 7、9 章并全量回归 |
| B4 | **ArkTS 静态类型限制**：禁 `any`/`unknown` 滥用、部分对象解构/展开受限、`JSON.parse` 结果不可直接信任、`Map` 不便 JSON 序列化 | 统一用 `Record<string,string>` + 显式类型校验；解析后逐字段白名单校验（EX-04） |
| B5 | **冷启动竞态**：Preferences `getPreferences/get` 为异步，若 UI 先渲染默认态再 hydrate，会出现状态跳变且可能把默认态覆盖写回 | `await restore()` 完成后再渲染业务页，期间显示加载态；F6 数据流 |
| B6 | **高频写盘**：Slider 拖动过程每次 onChange 都写盘会造成主线程 JSON 序列化卡顿 | 只在 `onChangeEnd` 提交；评估路径 `await save()` 后再反馈成功 |
| B7 | **状态管理版本混用**：ArkUI V1（`@State/@Link/@Provide/@Consume`）与 V2 装饰器混用易导致刷新异常 | 本期统一 V1；如选 V2 须在架构文档中明确并全量一致 |
| B8 | **场景可复现性**：场景加载是否重置设备会直接改变 7.5 的 `NO_CHANGE`/`APPLY` 计数 | 默认 `resetDevices=true`；「连续演练」作为 P1 独立开关，不混入预设场景预期 |
| B9 | **日志膨胀与备份键**：`app_state_backup` 与 `records` 200 条上限同时存在，序列化体积需可控 | 裁剪后再序列化；`records` 中 `snapshot` 保留但 `reason` 文案精简 |
| B10 | **模板工程一致性**：`main_pages.json` 当前只有 `pages/Index`，新增页面须登记；`List.test.ets` 须注册新测试套件 | 架构文档列出需改动的配置文件清单，避免「能编译但页面/测试不生效」 |
