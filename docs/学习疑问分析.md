## 1. 结论速览

**一句话结论**：官方《Local Test》指南明确「当前不支持测试 C/C++ 方法及**系统 API**」，因此 `@ohos.data.preferences` / `@kit.ArkData` 这类模块不能直接进 `entry/src/test/`；《栖居联动》的正确解法不是给系统 API 打 Mock 补丁，而是把规则引擎做成**零 `@ohos.*` 依赖的纯逻辑模块**、把系统依赖收敛到唯一的 `IStateRepository` 层并在测试中用内存替身注入——这一结论直接决定了 PRD 的分层与 12 条单测能否在无设备/模拟器下真实运行。

### 4.1 每份资料的关键内容与我的判断

| 编号 | 关键内容（官方要点） | 我的判断 |
|---|---|---|
| **R1** | ① 开篇限制：「**当前不支持测试 C/C++ 方法及系统 API**」；② 测试文件建议放待测试模块的 `test` 目录；③「手动创建后，需要在 **List.test.ets** 文件中添加创建的用例类」；④ 可按目录 / 文件 / 套件 / 方法四级运行 | **直接回答 Q-a**：Local Test 测的是纯 ArkTS 业务逻辑，不是系统能力。③ 也解释了模板里为什么有 `List.test.ets`，并成为 PRD 第 9 章「新套件必须注册」的依据 |
| **R2** | 框架为单元测试框架（JsUnit / hypium），以 **ohpm 包独立发布**，在 `oh-package.json5` 的 `devDependencies` 配置版本号；示例为 `"@ohos/hypium": "1.0.25"`；基础流程 `describe` / `it` / `expect` | **本地 `oh-package.json5` 实测值与官方示例逐字一致**（1.0.25），这是「为什么信这份」最硬的证据；也确认 12 条用例的写法与模板一致 |
| **R3** | Preferences 需 `getPreferences(context, …)` / `put` / `flush`，依赖 UIAbility context 与系统能力 `SystemCapability.DistributedDataManager.Preferences.Core`；约束：**非线程安全、多进程可能文件损坏和数据丢失**、建议数据量**不超过一万条**、key ≤ 1024 字节、字符串 value ≤ 16×1024×1024 字节 | **回答 Q-b**：它确实是系统 API，必须隔离到单独一层；「建议不超过一万条 / 内存随数据量增大」也直接支撑 PRD 把 `records` 上限定为 **200 条 FIFO** 与「单文档整体序列化」的设计 |
| **R4** | 可在 `src/mock/mock-config.json5` 中配置 `"@ohos.i18n": { "source": "src/mock/Language.mock.ets" }`，把系统 API 模块**替换**为 Mock 实现，从而在 `src/test/LocalUnit.test.ets` 中调用 | **回答 Q-c 但被我否决**：见 4.2，这是「模块替换」而非「真正测系统 API」，会引入与真机行为不一致的风险 |
| **R5** | 示例用 `import dataPreferences from '@ohos.data.preferences'`，并给出 **FA 模型** `featureAbility.getContext()` 写法 | **排除**：本工程是 **Stage 模型 / API 26**，新版指南用 `import { preferences } from '@kit.ArkData'` + `UIAbility`；照抄会直接编译失败 |

### 4.2 为什么 R4 的「Mock 系统 API」方案没有被采用

| 理由 | 说明 |
|---|---|
| 不改变能力边界 | R4 是**用 Mock 实现替换模块**，测的是替身的行为，不是 Preferences 的真实持久化；R1 的「不支持测试系统 API」依然成立 |
| 与真实环境有偏差 | 本项目的核心验收点是「杀进程重启后设备/规则/环境/日志逐项恢复」（PRD AC-07、T11），真值必须来自真机/模拟器上的 Preferences；Mock 出的「成功」不能作为交付证据 |
| 维护成本 | 需同时维护 `mock-config.json5` 与 mock 实现文件；本地工程该文件目前是空 `{}`，引入它等于给 12 条用例增加一层隐性依赖 |
| 有更干净的替代 | 用 `IStateRepository` 接口 + `InMemoryStateRepository` 替身，通过**构造函数注入**，测试完全不碰 `@ohos.*`；接口契约由 PRD 第 5.2 节冻结，改动面更小 |
| 结论 | **不采用 R4 作为主方案**，但保留其作为「未来若必须测含系统 API 的中间层」的备选知识，并在报告中写明取舍 |

## 5. 主要结论

| # | 结论 | 依据 |
|---|---|---|
| C1 | Local Test 的边界是「**不能测系统 API 与 C/C++ 方法**」，不是「不能测业务逻辑」；纯 ArkTS 的条件判断、排序、冲突裁决、序列化结构完全可测 | R1 |
| C2 | 因此 **M1 `RuleEngine` / M2 `Models` / M3 `MockEnvironmentProvider` 必须零 `@ohos.*` 依赖**；系统 API 只允许出现在 M4 `StateRepository`、M6 UI、M8 `EntryAbility` | R1 + R3 + 本地目录事实 |
| C3 | 持久化层必须抽象为 `IStateRepository`，测试用 `InMemoryStateRepository` 注入；这样「真实运行测试」与「进程重启恢复」两个评分点都能各自拿到证据，互不冒充 | R3 + R4 的否决结论 |
| C4 | 引擎须为**纯函数**：不修改入参、不调 `Date.now()`/随机数、不落盘；`now`、`recordId` 由调用方传入，断言才稳定可回归 | R1 + PRD 第 3.2 / 7.4 节 |
| C5 | 新测试套件必须在 `entry/src/test/List.test.ets` 注册，否则「能编译但用例不执行」 | R1 ③ |
| C6 | 数据量约束要落到设计：Preferences 建议 ≤ 一万条且内存随数据量增大 → 本作品 `records` 上限 200 条 FIFO，滑杆只在 `onChangeEnd` 提交 | R3 |
| C7 | 最终可测形态：**12 条 Local Unit Test（正常 6 / 边界 4 / 异常 2）在无需设备/模拟器的前提下真实运行**；持久化与恢复另用模拟器人工验收 + T11 内存替身用例覆盖 | R1 + R2 + PRD 第 9 章 |
