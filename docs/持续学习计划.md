## 7. 版本选择判断（本人判断）

| 判断 | 依据 |
|---|---|
| **交付坚持 26.0.0 Release，不采用 26.0.1 Beta1** | T3 对 26.0.0 的建议是「推荐使用 / 推荐升级」，对 26.0.1 Beta1 是「按需使用 / 按需升级（如需体验尝鲜）」；T6 官方阶段定义中 Beta 为「features that are approaching stability…Provide feedback」，Release 才是「Production-ready build with stable features and committed quality」。作业交付需要可复现、可验收的稳定基线，Beta 不适合 |
| **学习重心放在 Y（26.1.0）与 X（27.0.0），而非 Z（26.0.1）** | T4：Z 修订版本只做「问题修复和小改进，保持向后兼容」，Y 次版本才「包含新功能」，X 主版本「可能包含 API 修改，需要应用适配」。因此 26.0.1 只需做 A3–A5 回归验证，真正需要重学的是次/主版本 |
| **「版本号格式调整」本身就是一个必须学的知识点** | T4 明确「应用中涉及 API 兼容性判断的代码也需要随之进行优化」，T5 又说明「不影响兼容性判断的基本逻辑」——两者结合意味着：判断逻辑不变，但**判断所依据的版本号写法变了**，这正适合作为 W3 的实操题目 |
| **本工程 `6.1.1(24)` 基线不能顺手升上去** | 作业硬约束 + T5 三者约束与版本关系；把 `compatibleSdkVersion` 设低意味着要对不可用 API 做兼容性检查（T5 / T8），独立完成场景下不该引入这类额外风险 |
| **与新技术认识联动** | V2 迁移可行性不在本任务中直接实施，而是复用 `docs/新技术认识.md` 第 5 节 7 条局限做「收益 / 成本」判断，形成两份报告互相印证的证据链 |
